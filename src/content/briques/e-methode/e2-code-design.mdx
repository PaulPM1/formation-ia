## Cap

**Objectif :** comprendre l'organisation de ce que l'IA produit : non pas pour écrire le code soi-même, mais pour pouvoir le relire, le faire évoluer et ne pas subir son propre projet.

- Durée cible : 15 minutes.
- Prérequis : B4, « Claude Code » (un projet généré existe déjà).
- Résultat attendu : vous savez expliquer la structure de votre projet et pointer le fichier à modifier pour un changement donné.

## Concept durable

Un projet n'est pas un bloc de code : c'est un ensemble de fichiers qui ont chacun un rôle. Vous n'avez pas besoin de savoir maçonner pour lire le plan d'une maison : cuisine, chambres, tableau électrique. Un projet se lit de la même façon : interface (ce qu'on voit), logique (ce que ça fait), données (ce que ça retient), configuration (comment ça tourne).

Le principe central est la **séparation des responsabilités** : un fichier, un rôle. Elle permet de changer une pièce sans casser le reste. Un fichier unique de deux mille lignes qui fait tout est un signal d'alarme, pour vous comme pour l'IA : un agent modifie mieux un projet bien rangé. L'architecture n'est pas un luxe d'expert : c'est ce qui rend la modification suivante possible.

Le risque propre au développement assisté par IA est un projet qui fonctionne mais que personne ne comprend. Il devient alors impossible à faire évoluer, et chaque correction en casse une autre. Le test des trente secondes : si vous ne pouvez pas expliquer votre projet en trente secondes, vous ne le contrôlez plus.

Dernier réflexe : exiger une architecture simple. Pour un mini-outil, trois fichiers bien nommés valent mieux qu'une structure de framework complète. La sur-ingénierie est aussi un défaut de design.

## Pratique avec Claude

Ouvrez le projet créé en B4 et demandez :

```text
Décris le rôle de chaque fichier de ce projet en une phrase, sans jargon.
Puis dis-moi lequel je devrais modifier pour changer la couleur du titre,
et lequel pour ajouter une nouvelle fonctionnalité de rappel quotidien.
```

La carte d'un projet s'interroge sans lire son code. Si la réponse ne distingue pas clairement les rôles, c'est le projet qui a un problème, pas la question.

## Mission commune

Sur votre propre projet issu de B4 :

1. Demandez à Claude la carte du projet : rôle de chaque fichier en une phrase.
2. Choisissez une modification que vous aimeriez faire et demandez où elle vivrait, sans la réaliser.
3. Posez la question de contrôle : « Y a-t-il un fichier qui fait trop de choses ? Si oui, comment le découper ? »

**Critère de réussite :** vous savez restituer la carte de votre projet à voix haute, sans notes, en moins de trente secondes.

## Livrable

La carte de votre projet : une liste de vos fichiers avec leur rôle en une phrase, plus l'emplacement identifié de votre prochaine modification.

## Notes formateur

- **0–4 min :** l'analogie de la maison et les quatre zones (interface, logique, données, configuration).
- **4–7 min :** séparation des responsabilités + le signal d'alarme du fichier fourre-tout.
- **7–12 min :** mission commune sur les projets des participants.
- **12–15 min :** deux ou trois participants restituent leur carte ; test des trente secondes.

Message essentiel : « vous ne relisez pas le code ligne à ligne, vous vérifiez que la carte est logique ». Ne pas dériver vers le jargon (MVC, patterns, couches) : rester au niveau de la carte. Cette brique rassure ceux qui pensent que « le code, ce n'est pas pour eux ». Transition : une bonne carte rend possible l'itération par petits pas, objet de E3.

## Défis avancés

- Demandez à Claude de proposer un découpage d'un fichier trop chargé, et faites-lui justifier chaque nouveau fichier.
- Comparez deux architectures proposées pour le même besoin et demandez les compromis de chacune.
- Introduisez volontairement une demande floue (« améliore le projet ») et observez pourquoi le résultat est moins bon qu'une demande localisée sur un fichier.

## Variantes

- **Sans projet B4 :** utiliser un projet d'exemple préparé par le formateur, avec un fichier volontairement fourre-tout à diagnostiquer.
- **Non-développeurs :** appliquer la même grille à un dossier de documents (un dossier, un rôle) pour ancrer le principe hors code.
- **Initiés :** nommer les conventions du framework utilisé et vérifier que le projet les respecte.

## Dépannage

- **« Je ne comprends pas la réponse de Claude » :** demander une reformulation « comme à quelqu'un qui n'a jamais codé », une phrase par fichier.
- **« Mon projet tient dans un seul fichier » :** normal pour un mini-outil ; demander à partir de quelle taille il faudrait découper, et selon quels rôles.
- **« Claude propose une refonte complète » :** refuser ; demander le plus petit changement qui améliore la structure. La refonte totale est rarement la bonne première étape.
